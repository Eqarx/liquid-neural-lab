| 平板 1024×768 | `pointer: coarse` 生效 ✓；工具条按钮 71×44（≥44px）✓；层级/面板开关高 40px ✓；无横向溢出 ✓；浮窗栈与工具条零重叠 ✓ |

本轮修掉的真实缺陷（都经实测复现 + 修后复测）：

1. **鼠标滚轮先平移后缩放**（严重）：用 `deltaY % 40` 猜设备，而 Windows 滚轮报 100（不匹配 → 被当成触控板去平移）、个别事件报 120（匹配 → 缩放），同一串滚动行为不一致。改为**按滚动会话锁定设备**（相邻事件 <260ms 视为同一次手势，首个事件判定）。
2. **触控板平移方向反了**：滚轮路径误用了"内容跟手"（拖拽语义），改为文档语义（向下滚 = 视口下移）。
3. **Ctrl+滚轮缩放不累加**：每次以滞后的 k 为基准，快速捏合被吃掉大半（改为以弹簧目标值为基准累乘）。
4. **`flyTo` 后缩放弹簧目标陈旧**：点过「输入格/全览」再捏合会被往回拽（实测 k 1.15 → 0.735）。
5. **滚轮平移被惯性项放大**：5×14px 的滚动变成 51px，极端可达 16 倍（滚轮路径不再加惯性，并对拖拽路径加了速度上限）。
6. **捏合时平移被缩放锚点每帧覆盖**：两指拖动几乎不动（改为地图式手势数学 `pinchTo`，缩放与平移一体、1:1 跟手）。
7. **触摸捏合会先在画板上戳一个墨点**：改为"按下先不落墨，判定为手势则整笔还原；轻点仍落子"。
8. **窄屏聚焦没考虑浮窗占位**：输入格有一半压在面板下，手指点上去其实点在面板上（改为按"顶栏底边 ~ 浮窗顶边"的实测可见带取景）。
9. **窄屏顶栏塞不下**：「体验/探索/专家」被挤成竖排两行并压住输入格（改为窄屏隐藏品牌文字、按钮不折行、允许整行换行）。
10. **触摸移动会留下不消失的悬停浮层**（触摸不再触发 hover）。

## 4c. 管道亮度的语义修正（"最亮的来路 = 答案"）

现象：偶尔出现「识别为 3，但最亮的管道指向 9」。用 12 个内置样本量化后确认这不是偶发：

| 判据 | 修正前 | 修正后 |
| --- | --- | --- |
| 最亮管道的目标 = 预测数字 | 3/12 | **12/12** |
| 单一数字的能量和最大者 = 预测数字 | 7/12 | **12/12** |

两个原因（都是**可视化取值**问题，不是模型问题）：

1. 亮度用了 `|w·a|`（绝对值）→ **抑制性连接**（把该数字往下压的负贡献）被画得和兴奋性一样亮。
2. 每个数字只画它最强的 3 条连接，其"能量和"本来就 **不等于**该数字的总推动量 —— 赢家可能靠大量中等贡献取胜。

修正后的显示规则（已写进图例）：

- 单根管道能量 = 该数字的**整体推动量占比** × 这根管道在该数字内部的**贡献占比**；
- 整体推动量 = 对**全部**输入求和（不只显示的那几根）；输出层用 **softmax 概率**（相对最大概率），其余层用层内最大总正向推动归一化；
- 只统计正向推动 `max(0, w·a)`，抑制性连接画成深灰空管。

这样"最亮/最粗的来路"必然通向答案，同时单根之间的差异仍然真实反映各连接的贡献占比。

| 指标 | 数值 |
| --- | --- |
| JS 帧耗时（场景更新 + 绘制命令） | 1.1 – 2.5 ms |
| 应用渲染成本（有头 Edge，离屏窗口） | ≈ **1.5 ms/帧**（同环境空转 61fps → 应用 56fps） |

手段：拓扑从 28,512 条线降为 58 根管道；管道分"点亮 / 空管"两条渲染分支（空管只描两次）；
能量光团只在点亮的管道上生成，拖尾按颜色批量描边；玻璃球渐变按需创建；
管道几何只在节点移动 / 换数字时重建；DOM 层标签只在渲染循环里写 `transform`，不触发 React 重渲染。

> 测量注意：无头浏览器用软件光栅化，帧率不代表真机；有头测试窗口被移到屏幕外，
> Chromium 会把离屏窗口降频（本机空转也只有 ~70fps），因此上表给出的是**相对成本**而非绝对帧率。

## 6. 已知问题与限制

1. **画面是示意拓扑（已在界面四处写明）**：每层只画最活跃的 8 / 6 / 4 个神经元与 58 根主管道，
   而真实前向传播使用全部 96 / 64 / 48 个神经元与 28,512 条连接。显示的**数值都是真的**
   （激活值、w·x 贡献、Softmax 概率、准确率），只有"画多少"是示意的。
   界面文案里的架构、连接数、准确率一律由 `manifest.json` / `metrics.json` 推导，不写死数字
   —— 训练脚本会整套重写权重 + 清单 + 指标 + 夹具，写死数字迟早会变成假声明（本轮就抓到过一次：
   一次实验性训练把模型换成 196-64-48-32-10，而文案仍写着 96/64/48 与 97.91%）。
2. **画面只点亮"贡献显著"的管道**：每层的管道贡献先按该层最大值归一化，再按显示阈值 0.24 压缩
   （低于阈值画成深灰"空管"）。因此同一层里能看到"有的管子通能量、有的空着"，但**所有连接都在参与真实计算**；
   图例中已注明。液面高度同样做了非线性压缩（`x^0.62`，封顶 0.82），否则输入稍大时每个球都会灌满。
3. **输入限制**：单数字分类器（0–9）。写多个数字、涂鸦或复杂背景时输出不可靠 —— 模型能力的真实边界。
4. **手写风格差异**：模型在 MNIST 风格（黑底白字、居中、粗细均匀）上训练；
   过细、断笔、倾斜过大的手写会低于测试集 97.91%。这是真实的域偏移，可用于教学。
5. **只读模型**：不包含浏览器内训练，专家面板中的参数只读。
6. **粒子是动画示意**：光团表示计算顺序与能量注入，网络内部并没有粒子在传输（图例已注明）。
7. **窄屏"全览"可读性有限**：手机竖屏把 4,400×600 的整张网络缩到 350px 宽后节点很小，
   此时建议用「输入格 / 隐藏层 / 输出层」按钮逐层查看（已自动上移避开底部浮窗）。
8. **画布键盘操作有限**：网络画布主要面向指针交互；键盘用户可通过结果面板、检查器、专家面板获得同等数据。
9. **中文字体为系统栈**：自托管字体仅含 latin 子集（Space Grotesk / JetBrains Mono），中文回退系统字体。
10. **Windows 开发环境**：Vite 使用轮询文件监听（原生 `fs.watch` 在本机频繁编辑时 EBUSY）。
11. **浏览器兼容**：面向现代浏览器（ES2020）；未使用 `@starting-style` 等前沿 CSS。
